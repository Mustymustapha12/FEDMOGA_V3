# AI development context — self-contained handover
FEDMOGA serves FGGC Minjibir Old Girls Association applicants, members and administrators. This repository is V3, derived from V2 2b3ca6ddbabbb8b6fd4438596fa0dd8a38f7f4b5, preserving Git history and the existing application. Target GitHub repository: Mustymustapha12/FEDMOGA_V3; working branch development/v3. Never modify V2 production, database contents, API keys or connections. Do not rebuild the UI.

Read AGENTS.md and all workflow docs linked by README before changing code. The exact schema is server/schema.ts; actual production schema has not been inspected. V3 adds two tables without changing existing columns. No live database import/export is authorized; staging uses fresh synthetic data.

Technology: Node >=22.13, Next.js 16.3.8, React 19.2.6, TypeScript, mysql2, Nodemailer. app/portal.tsx is the large existing public/admin client component; server route handlers enforce access. Admin pages are tab state within /admin, not one route per sidebar item. Shared /login identifies roles server-side; members go to /member. Public landing stays at /.

Authentication is separate admin/member hashed-token sessions with auth_version invalidation, enabled/active flags and eight-hour expiry. Only Super Admin manages Admin Users, bulk manual imports, mail processing/history and migration. Admin handles registration/member reporting, individual bank approval, form/fee and dues prices. Details APIs require Admin/Super Admin; members access their own state separately. Account Delete is soft deactivation with self/last-active protection and retained history.

Registration starts with payer identity and fee snapshot, initializes an attempt and verifies through server Paystack API; successful payment gives a 30-day single-use token for the published form. Server overrides fullName/email/phone with verified identity. The registration transaction writes registration, member/activation outbox and consumes the token. Pending/successful-but-incomplete payments must remain recoverable. Manual approved previous payments reuse the original approval service. V3 pending transfer claims confer no access until admin confirmation, which is locked/idempotent.

Payment validation checks success, reference, amount >= snapshotted amount, NGN, payer email and test/live domain. Signed webhook additionally verifies SHA-512 HMAC, then re-verifies server-side. Registration payments and member dues stay separate. No browser redirect establishes payment success. Do not change the allowance for customer-borne surcharge.

Calendar rules are fixed in server/calendar.ts: Lagos dates; monthly/quarterly/yearly calendar boundaries, early renewal after current paid_until, expired renewal from payment/current period, no proration or automatic historical arrears, no recurring deductions. finalizeDues locks member then payment and is idempotent. Outstanding means one next preferred-plan renewal at current configured price for an enabled unpaid member, not accumulated debt. Paid coverage and enabled login status are distinct.

Reports use app/report-data.ts plus server/report-query.ts. Registration reporting joins payment attempts to registrations/manual approvals and pending claims. CSV exports all matching rows across pages, and serial numbering is separate from permanent registration numbers. Member reports use mode-scoped data, paid/owing/status/plan/expiry/date/demographic filters. Pagination is in-memory, not SQL streaming; this remains a scaling limitation.

View repair: V2 registration reports omitted onView, member lists omitted profile handlers, and the old detail block displayed paymentId as a transaction reference. V3 passes explicit kind/id to /api/admin/records, fetches authoritative joins, returns 400/404 for invalid/missing records, removes secret fields, and renders a shared detail panel. Source findings are verified; production browser reproduction is not claimed. Tests must continue to cover different users, types and payment states.

Email: existing branded SMTP/outbox and calendar reminders retained. Manual V3 dues campaigns require signed 10-minute previews, selected recipient/balance/period review and confirmation. The send transaction revalidates data, only enabled owing members qualify, dedupe keys suppress identical daily reminders, and dispatch cancels paid/disabled members. Existing advance scheduled renewal notices remain separate. email_attempts stores attempt history; SENT means accepted by SMTP, not inbox delivered. Failures retry to ten attempts; Super Admin can retry specific jobs. Exactly-once SMTP cannot be guaranteed across crashes.

Configuration: APP_URL, DB_*, bootstrap credentials, encryption key, live toggle, SMTP_*, JOB_SECRET; see environment guide. Paystack keys/fee/form/dues prices are settings, with encrypted secrets. Preserve encryption-key compatibility for any authorized later restore. For staging, mandatory FEDMOGA_ENV=staging, separate DB ending _staging/_test, test keys only, no live toggle, isolated SMTP plus STAGING_EMAIL_SINK. The sink rewrites recipients. Never copy production queues, keys or PII into staging.

Deployment: separate Hostinger Node application and DB. Build npm ci + npm run build, start npm start. Call /api/jobs/run every ten minutes with separate Bearer JOB_SECRET; workflow included. No hosted staging URL exists until credentials/domain/access are supplied. No production cutover is authorized. Rollback redeploys a previous V3 commit against its isolated database and retains additive tables; V2 needs no rollback.

Tests: node --import tsx --test --test-concurrency=1 tests/*.test.ts. Without FEDMOGA_APP_TEST_URL and FEDMOGA_RUN_DB_TESTS=true, integration tests skip. Use a dedicated _test DB, running production build and synthetic/mock payment/email services. Existing tests must remain; relevant new tests are v3-policy and v3-integration. Validation records exact executed counts and limitations. No dedicated lint tool exists; typecheck/build/Prettier are supported.

Known limitations: in-memory dataset filtering, latest-200 mail dashboard, no delivery/bounce provider integration, at-least-once SMTP, no public bank-proof upload, manual historic source ambiguity, no versioned ALTER migrations, hosted/browser acceptance pending where unavailable. Do not fabricate credentials, successful deploys, test outcomes or production verification.

Continue safely: verify working tree/branch, read docs, inspect APIs + DB relationships, implement incrementally on V3, test isolated workflows and update docs/changelog. GitHub write authentication and hosting access can block publication, but local work should remain reviewable. Production/destructive changes need explicit approval.
